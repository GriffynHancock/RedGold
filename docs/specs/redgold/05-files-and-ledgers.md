## 7. The three files

The prior engagement's ledger failed because one file served five purposes. Each file below answers exactly one
question, and content answering a different question is a defect.

### 7.1 `CLAUDE.md` — the constitution

*"What are the rules here?"* Auto-loads every session; re-injected after compaction. Written at
scaffold, changed only by deliberate amendment. Hard cap **120 lines** (Anthropic recommends under
200; adherence degrades past that as the model samples rather than reads).

Contains: what this engagement is; the top constraint; ROE; the declared mode and ceiling; a
*pointer* to `scope.yaml` (never a copy); the file contract; output discipline; model policy;
the escalation rule for mistakes (§13).

**Test: would this be equally true on day 1 and day 20?** If no, it does not belong. No findings,
no progress, no history.

### 7.2 `status.md` — the ledger

*"What is true right now?"* Present tense, current state only:

- phase table with owner and state
- active gate and current ceiling
- open blockers
- **open cleanup debt** (§9.4) — the engagement cannot close while this is non-empty
- findings index: ID, one line, PROVEN/SPECULATED, `verified` level, severity — **pointing at**
  `findings/*.json`, never copying them

**Generated by `scripts/regen_status.py` from `ledger/` + `findings/`.** It is a view, not a
source, so it cannot drift and cannot grow a duplicate ID.

**Nothing writes to `status.md` directly — ever.** An agent that needs to raise a blocker appends to
`ledger/blockers.jsonl`; phase state goes to `ledger/phases.jsonl`; the view is then regenerated.
Earlier drafts told agents to "write a blocker to `status.md`", which would have silently broken the
regeneration guarantee the moment it happened.

**Test: is this still true this minute?** Anything about the past belongs in `session.md`.

### 7.3 `session.md` — the working log

*"What happened, and what should the next session know?"* Append-only, one per session: what was
attempted, what failed and why, decisions with reasoning, dead ends worth not repeating. Ends with
a **handoff block** in a fixed format. Archived to `ledger/sessions/NNN-YYYY-MM-DD.md` on close.

A `SessionStart` hook injects the previous handoff block. This is the artifact that survives
context compaction — conversational instructions that were never written to a file are lost
outright at compaction, and nested CLAUDE.md files are not re-injected.

**Test: would deleting this lose reasoning?** It is never the source of truth for a finding.

The handoff block is fixed-format, because `session_start.py` injects it verbatim and it is the one
artifact designed to survive context compaction:

```markdown
## HANDOFF
- **Phase:** P3-webtest (in_progress)
- **Plan:** PL-001, approved 2026-08-05, max_tier 2
- **Done this session:** authz boundary tests on A-014 (9 checks, 1 finding F-007)
- **Open blockers:** B-003 (deviation: /rest/v1/referrals not in plan)
- **Cleanup debt:** 2 rows pending on /rest/v1/email_subscription
- **Next action:** re-plan to include referrals, or de-scope it
- **Do not repeat:** anon delete fails on email_subscription — use cleanup credential
```

Every field is required; `none` is a valid value. The `Do not repeat` line is the cheapest defence
against the same dead end being re-explored tomorrow.

### 7.4 The invariant

**No fact lives in two files.** `status.md` indexes findings; `session.md` narrates work; findings
live in `findings/*.json`; approvals live in `ledger/gates.jsonl`. Duplication is the bug that
produced the prior engagement's drift.

### 7.5 Ledger schemas

`status.md` is regenerated from these, so they are load-bearing and specified at the same rigour as
the findings schema.

```jsonc
// ledger/gates.jsonl — one record per approval decision
{"id":"G-002","gate":1,"decision":"approved","tier_authorised":1,
 "scope_hash":"sha256:…","requested_by":"rg-webtest","approved_by":"operator",
 "rationale":"bundle indexing only, no writes","ts":"2026-08-06T09:31:00Z"}

// ledger/activity.jsonl — append-only. Every action that touched the target.
{"ts":"…","agent":"rg-recon","action":"http_get","target":"api.acme.example",
 "tier":1,"purpose":"attribution","gate_ref":"G-002","tool":"curl",
 "outcome":"200","evidence_ptr":null,"model":"sonnet","escalation_reason":null}

// ledger/cleanup.jsonl — every write, and whether we got it back out
{"id":"C-004","endpoint":"/rest/v1/email_subscription","method":"POST",
 "canary_id":"rg-canary-8f21","created_ts":"…","delete_verified":true,
 "state":"deleted","deleted_ts":"…","note":null}
```

```jsonc
// ledger/phases.jsonl — phase state. Source for status.md's phase table.
{"phase":"P2-surface","owner":"rg-surface","state":"in_progress",
 "started":"…","ended":null,"plan_ref":"PL-001","note":null}

// ledger/blockers.jsonl — anything that halts work and needs the operator
{"id":"B-003","raised_by":"rg-webtest","kind":"deviation",
 "detail":"endpoint /rest/v1/referrals not named in plan PL-001",
 "raised":"…","resolved":null,"resolution":null}
```

`kind` is one of `deviation` (Gate 2), `cleanup` (unrecoverable write), `validation` (two failed
correction attempts, §9.6), `capability` (a tool or credential is missing), or `decision` (a genuine
judgement call for the operator).

`scope_hash` on a gate record pins the exact scope the approval was granted against, so an amended
scope cannot silently inherit an older authorisation. `state: orphaned` in `cleanup.jsonl` is what
`cleanup_gate.py` blocks session end on. An unresolved row in `blockers.jsonl` blocks phase advance.

### 7.6 The test plan — `ledger/plan.json`

Gate 1 approves *this file*. Without it as a real artifact, "deviation stops and asks" is
unenforceable prose (see §9.3.2).

```jsonc
{
  "plan_id": "PL-001",
  "scope_hash": "sha256:…",
  "approved_by": "operator",
  "approved_ts": "2026-08-05T09:00:00Z",
  "max_tier": 2,
  "phases": [
    {
      "phase": "P3-webtest",
      "assets": ["A-014", "A-021"],
      "test_classes": ["authz-boundary", "rate-limit", "input-reflection"],
      "write_endpoints": [
        {"method": "POST", "route": "/rest/v1/email_subscription", "max_writes": 10}
      ],
      "expected_cleanup": "delete by RedGold-TEST marker",
      "live_confirm": ["rate-limit"]
    }
  ]
}
```

`live_confirm` names test classes that still require an in-the-moment operator check despite being
in the plan — the escape valve for anything the operator wants to watch happen. Everything else in
the plan runs unattended.

`plan_hash` on a gate record is the SHA-256 of this file. Editing the plan voids its approval.
