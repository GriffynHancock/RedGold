# Prior-engagement autopsy

Read-only forensic review of `ENGAGEMENT-B` and `ENGAGEMENT-A`. No file in
either engagement, in `~/<target>`, or on any target was modified; no request was issued.

Every claim below cites a path and line. Anything I could not establish from files on disk is
marked `[UNVERIFIED]`, per hard rule 1 — including where that cuts against the conclusion I would
prefer.

**Headline.** Eleven findings reached `status.md`. One is a genuine, production-relevant, correctly
rated result (`F-011`). Three are correctly rated low posture facts. Seven — including the single
critical and two of the three highs — are artifacts of testing a Docker **dev stack** on the
operator's laptop and reporting its dev-only components as if they were the client's production
system. Separately, the largest real risks in this codebase were never looked for: the whitebox
engagement, which held the source-code asset, produced **zero** artifacts of any kind.

The operator's verdict is confirmed and is more precise than "noise": the engagement's reasoning
was locally sound at every step and never once asked *what environment am I in* or *what does the
attacker already have to hold*. Those two omitted questions generate all seven bad findings.

## B. Verdict per finding

### F-107 — magic-link → Mailpit account takeover (claimed **critical**)

**Verdict: DEV-STATE ARTIFACT, with a PRECONDITION-INVERTED component.**

The chain has three legs: (1) `POST /members/api/send-magic-link/` accepts an arbitrary address
unauthenticated; (2) the token is delivered in plaintext by email; (3) that email lands in an
unauthenticated Mailpit instance readable by anyone with network reach. Legs 1 and 2 are stock
Ghost and are *not* defects — they are how passwordless auth works everywhere. The entire finding
is leg 3, and leg 3 exists only because the app's mail transport points at a development mail
catcher.

The finding says so itself. Its own remediation, `findings/webtest.json:115`, asks the client to:

> "(2) confirm Ghost's mail transport in this environment is genuinely intended to be Mailpit
> rather than a real SMTP relay — **if** this pattern … exists in any non-ephemeral/production-adjacent
> environment, magic-link authentication itself becomes a full account-takeover vector"

That is a `critical` severity conditioned on an unresolved question about the environment. The
question was answerable — `pre-audit.md:270` answers it, and the finding's own sibling
`F-103` calls Mailpit *"a development/test tool"* in its remediation text
(`findings/webtest.json:47`). Nothing in the engagement is wrong about the mechanics. The severity
is assigned to a deployment that was never shown to exist.

The precondition-inversion is the second half. `F-107`'s impact claim
(`findings/webtest.json:114`) is that an attacker can sign in as one member. The capability it
requires is unauthenticated read of *every message in the environment's mail spool* — which is
`F-103`, rated `high`. Reading all mail strictly dominates signing in as one member: it also yields
password resets, submission notifications, and every future token. So `F-107` does not escalate
over its own precondition; it restates it and rates the restatement one level higher.

Note also `verified: "executed"` is doing double duty. The token read was executed. The takeover
was not — `findings/webtest.json:114` states plainly: *"the takeover capability for a real account
is reasoned from the observed mechanics … not from having been repeated against a real account."*
The `verified` field attaches to the primitive; the `critical` attaches to the reasoned impact.
Nothing in the schema notices the gap.

### F-005 — "Admin API reachable anonymously" (claimed **high**)

**Verdict: MISCLASSIFIED-SEVERITY, shading into TRIVIA.**

`evidence/F-005-ghost_admin_open.http:16` is the whole response body:

> `{"site":{"title":"<Target>","description":"Your own platform to share knowledge and get paid.",
> "logo":null,"icon":null,"cover_image":null,"accent_color":"#9a4a21","locale":"en",
> "url":"https://…/","version":"6.45","allow_external_signup":true,
> "site_uuid":"fac8bd3d-55c1-458a-89a4-a7bd02f6f63c"}}`

Site branding and a version string. `/ghost/api/admin/site/` is Ghost's designed-public route — the
admin login page fetches it before any session exists. The engagement's own surface map says so:
`assets/surface-map.md:27` describes the sibling `/ghost/api/admin/authentication/setup/` as
*"Ghost's designed-public route … not a misconfiguration by itself"*, and `surface-map.md:48`
concludes *"the admin API is **not** wide open beyond `/site/` and `/authentication/setup/`"*.
`findings/webtest.json:80` (F-105) independently files near-identical disclosure at `info`.

`findings/verification.md:171-186` caught this and argued it correctly:

> "Compare directly against F-105, filed at info for disclosing near-identical content … No admin
> capability, no write access, no member data, no session, no credentials are exposed … I'd
> recommend downgrading this to low"

The recommendation was never applied. `findings/baseline.json:71-84` still reads `"severity":
"high"`, and `status.md:55` still lists it as high. See D and FM-4.

### F-101 — Redis unauthenticated (claimed **high**)

**Verdict: DEV-STATE ARTIFACT; impact magnitude UNFALSIFIABLE as stated.**

The fact is real and reproduced twice (`findings/verification.md:83-93`). Two problems with the
finding as filed.

First, the configuration is deliberate dev config, not drift — `pre-audit.md:24-27` traces
the `0.0.0.0` bind to `compose.dev.yaml`. A production Ghost deployment does not publish Redis to
the host network; the container name is literally `<app>-dev-redis`. `[UNVERIFIED]` whether a
production compose/manifest for this app exists or what it binds — I have no such file on disk.

Second, the `high` is justified in `findings/webtest.json:12` by an escalation that was explicitly
not performed:

> "unauthenticated Redis is a well-known path to full remote code execution via CONFIG SET
> dir/dbfilename + SAVE … **this instance was not tested for either technique** because both are
> destructive/out of scope"

That is §10.4 gate 5 ("Real vulnerability — PASS requires a demonstrated exploit path") failing on
the finding's own text, and it is the reason the record carries `high` rather than the `medium` its
demonstrated content supports.

Third, the blast radius — *"Any host that can reach TCP 6379 on this tailnet"* — is the entire
severity argument and was never enumerated. Nothing on disk records how many devices are on
`<tailnet>.ts.net`, who owns them, or what the tailnet ACL permits. The claim is not false;
it is unfalsifiable as written, because its scope was never established.

### F-103 — Mailpit HTTP API unauthenticated (claimed **high**)

**Verdict: DEV-STATE ARTIFACT.**

Mailpit ships with no authentication because it is a local mail catcher for development. The
finding's own remediation says it: *"Mailpit is a development/test tool and should never be
reachable from a shared network segment in any environment that also carries real application
mail"* (`findings/webtest.json:47`). The conditional in that sentence — *"in any environment that
also carries real application mail"* — is the whole question, and `pre-audit.md:270`
answers it: this environment does not carry real mail; Mailpit **is** the transport precisely so
that no real mail is sent.

The finding is a true statement about a dev tool doing its job. The correct output was a note in
the environment section of the report, not a `high`.

### F-046, F-058 — missing HSTS on Mailpit `:8025` / `:8026` (claimed **low**)

**Verdict: TRIVIA — the check is logically void on these assets.**

`evidence/F-046-header_strict_transport_security.http:1` shows the request scheme:
`GET http://host.example.ts.net:8025/`. `Strict-Transport-Security` served
over plaintext HTTP is ignored by user agents; asking a plain-HTTP origin to set it is not a
finding, it is a category error. The engagement knew — `assets/surface-map.md:115` writes
*"still lacks HSTS (moot on plain http)"* — and filed the records anyway, because the record was
generated by `baseline_scan.py` before any human sentence was written about it.

The stated impact compounds it: `"HSTS not set; a downgrade to plaintext is not prevented"`
(`findings/baseline.json`, F-046/F-058) — on a connection that is already plaintext.

### F-048, F-060 — missing X-Content-Type-Options on Mailpit (claimed **low**)

**Verdict: TRIVIA + DEV-STATE ARTIFACT.**

True (`evidence/F-048-header_x_content_type_options.http:4-10` shows the header absent). It is a
defence-in-depth header missing on a dev mail catcher's UI, which serves no client data and exists
in no production deployment. §10.5's own false-positive table says the general case out loud:
*"Missing security headers with no exploit | Defence-in-depth, not a vulnerability"*
(`docs/specs/redgold/08-findings-and-verification.md:125`).

F-060 is additionally a duplicate: `assets/register.jsonl:5` establishes that `:8026` is *the same
Mailpit process* as `:8025` (byte-identical body, same database path, same uptime to the second).
Two ports, one process, two findings.

### F-010, F-011, F-012 — missing HSTS / CSP / X-Content-Type-Options on the Ghost host

**Verdict: SOUND at `low`.**

These are on the actual application over HTTPS, correctly classed `posture`, correctly rated `low`,
correctly carrying `verified: n/a` with a resolving evidence pointer. This is the framework's
posture carve-out (`docs/specs/redgold/08-findings-and-verification.md:66, 77-80`) doing exactly
its job. Would apply to a production deployment of this theme too. No complaint.

### F-102, F-105, F-106 — recorded negatives (`info`)

**Verdict: SOUND as records** — recording tested-and-clean is P10/P11 and is one of the better
things these engagements did (`docs/specs/redgold/01-principles.md:94, 108-112`).

**But F-106's conclusion is wrong**, and wrong in the reassuring direction. It states *"Anonymous
readers cannot read gated content through this key"* (`findings/webtest.json:97`), having tested
exactly one route — the public content API. See section F.1 for the route it did not test.

### F-104 — "MySQL requires authentication" (`info`, framed as a positive)

**Verdict: MISCLASSIFIED — under-rated, and the framing actively misleads.**

`findings/webtest.json:63`: *"Negative result, and a good one … MySQL demands credentials on this
host — it is not an open datastore the way Redis is."* One connection attempt, `root`, empty
password.

Ground truth (`pre-audit.md:33-36`): `bind_address = *`; **`root` and `ghost` both have
grant-host `'%'`**, i.e. remote login is not restricted at all; and the root password is
`${MYSQL_ROOT_PASSWORD:-root}` from the compose file — *"not printed here, but note its
weak/default-shaped provenance."* A single blank-password probe answering `ER_ACCESS_DENIED` was
converted into a reassurance about a service that is remotely reachable, remote-root-enabled, and
protected by a default-shaped secret.

`[UNVERIFIED]` whether the deployed root password is in fact the compose default — the operator
declined to print it and I have no compose file. The point stands regardless: the engagement had no
basis for the word "good", and a credential check was ruled out by plan constraints without the
resulting blind spot being carried into the finding.

## C. Root-cause taxonomy

Eight generative failure modes. The (iv) column is the one that matters for guardrail design.

### FM-1 — Environment blindness

**(i)** No step of the engagement ever established, recorded, or reasoned about whether the target
was a production deployment, so every dev-stack component was assessed as if it were serving real
customers.

**(ii)** F-101, F-103, F-107, F-046, F-048, F-058, F-060. Seven of eleven reported findings,
including the only critical and two of three highs.

**(iii)** Signals available *inside the engagement*, before any finding was written:
- The host is a Tailscale MagicDNS name for a named personal laptop —
  `host.example.ts.net` (`scope.yaml:20`). Not a domain a product is served
  from.
- Mailpit was CONFIRMED as an asset on three ports (`assets/register.jsonl:4,5,6`). Mailpit's
  presence is definitionally a dev signal; the engagement wrote the words *"Mailpit is a
  development/test tool"* into `findings/webtest.json:47` and *"a development/test tool"* is a
  complete environment classification on its own.
- Mailpit's database is `/tmp/mailpit-<nnnn>.db` (`assets/register.jsonl:4`) — an
  ephemeral path.
- The Ghost admin SPA and the member Portal bundle **both 502** (`assets/surface-map.md:167-172`).
  The application under test was not in a working state, which the engagement noted as an
  availability curiosity (`surface-map.md:190-193`) rather than as evidence about what it was
  looking at.
- `scope.yaml:40-44`'s `forbidden_actions` list is a near-verbatim restatement of
  `pre-audit.md:313-326`'s "Tell RedGold to avoid" list — so the pre-audit's content
  reached the engagement boundary, including its dev-config findings, but only the four
  cost-related items survived the transfer.

**(iv)** **Mechanically checkable, high confidence.** Hostname suffix, dev-tool service
fingerprint, and ephemeral-path detection are all string matches against data already sitting in
`assets/register.jsonl` and the evidence files. The judgement part is only the *consequence* of the
classification, and that can be a fixed policy (cap severity, stamp the report) rather than a
decision.

### FM-2 — Fixed severity table decoupled from the observed response

**(i)** Baseline severity is a constant attached to the check, applied whenever the check's boolean
returns true, with no reference to what the response actually contained.

**(ii)** F-005.

**(iii)** The response body was in hand at scoring time and contained nothing non-public
(`evidence/F-005-ghost_admin_open.http:16`). The predicate that fired is
`scripts/baseline_scan.py:104-106` — `_admin_reachable` is `return probe.status == 200`, nothing
more — and the severity comes from `scripts/baseline_scan.py:158` (`"high"` hardcoded in the
`Check` tuple) via `scripts/baseline_scan.py:235` (`"severity": check.severity if present else
"info"`).

**(iv)** **Partly mechanical.** "Does this 200 body contain anything a stranger shouldn't have" is
judgement in general. But the specific sub-case here is deterministic: a check whose *only*
predicate is `status == 200` cannot distinguish "endpoint exists" from "endpoint leaks", and
therefore must not be allowed to emit above `low` on its own. That rule is a one-line property of
the check definition, not of the response.

### FM-3 — Self-certified verification

**(i)** The component that discovers a finding also writes the field that attests it was
independently verified, so the framework's strongest severity rule can never fire on that
component's output.

**(ii)** F-005 (the only baseline finding above `low`; `verified: "executed"`,
`discovered_by: "baseline_scan"`, **no `verified_by` field at all**).

**(iii)** `scripts/baseline_scan.py:232-233` states the reasoning in a comment:

> `# An automated GET that observed the condition is a mechanical demonstration.`
> `"verified": "executed" if present else "none",`

That is defensible for the *observation* and inadmissible as *verification*. P2 is explicit:
*"A finding is not a finding until something other than the model has verified it"*
(`docs/specs/redgold/01-principles.md:24`), and §10.3 defines `executed` as *"The impact was
mechanically demonstrated"* — impact, not presence. `UNVERIFIED_ABOVE_LOW`
(`scripts/findings.py:274-280`) checks `verified not in VERIFIED_STRONG`; because the scanner wrote
`executed` itself, the rule was satisfied by the thing it exists to catch.

**(iv)** **Mechanically checkable, trivially.** `verified_by != discovered_by` is a two-field
comparison. This is the single cheapest repair on the list.

### FM-4 — Verification verdicts land in prose and are never merged

**(i)** `rg-verify` produces a narrative markdown document; findings records are JSON; nothing
transports a verdict from one to the other, so a correct rejection has no effect on anything
downstream.

**(ii)** F-005 (severity dispute raised, argued in detail, never applied).

**(iii)** `findings/verification.md:184-186` recommends the downgrade *and the retitle*:

> "I'd recommend downgrading this to low, with the title changed from 'Admin API reachable without
> authentication' to something like 'Admin site-config sub-route discloses branding and version
> info anonymously' so it doesn't read as a broader access-control failure than it is."

and `verification.md:251-252` records it in the summary: *"severity disputed — recommend downgrade
high to low."* `findings/baseline.json:78` still says `"severity": "high"`. `status.md:55` still
publishes it as high. The reasoning step succeeded completely and changed nothing.

**(iv)** **Mechanically checkable.** The gap is a file format, not a judgement. §10.4 already
specifies a per-gate verdict structure (`docs/specs/redgold/08-findings-and-verification.md:100-109`)
— it is simply not serialised.

### FM-5 — Reasoned escalation past the last executed step

**(i)** The severity is set by the worst outcome the mechanics *imply*, while `verified` is set by
the last step that was actually *run*, and no field distinguishes the two.

**(ii)** F-101 (RCE named as the severity justification, explicitly not attempted), F-107 (real
account takeover reasoned, explicitly not performed).

**(iii)** In both cases the agent wrote the disclaimer itself, in the same field as the claim:
*"this instance was not tested for either technique"* (`findings/webtest.json:12`); *"the takeover
capability for a real account is reasoned from the observed mechanics … not from having been
repeated against a real account"* (`findings/webtest.json:114`). The honesty was present; nothing
read it. §10.4 gate 5 exists for exactly this (*"FAIL when: Informational-only, best-practice,
self-XSS, or theoretical"*) and is not implemented anywhere in `scripts/`.

**(iv)** **Judgement in general — but with a high-yield mechanical proxy.** Deciding whether a
reasoned escalation is warranted needs a reasoning step. Detecting that the impact string contains
an admission of non-execution is a lint: `not tested`, `not attempted`, `not exercised`,
`reasoned from`, `well-known path`, `would allow`, `was not exercised here` all appear verbatim in
the two records concerned. A lint that routes such records to the report's open-questions section
would have caught both without adjudicating either.

### FM-6 — Chains rated by novelty rather than by capability delta

**(i)** A finding assembled from two other findings is rated above both, without checking whether
its capability actually exceeds the capability its own precondition requires.

**(ii)** F-107 (critical) over F-103 (high), where F-107's exploit requires F-103's capability and
yields strictly less.

**(iii)** Both records were in the same file, written in the same session, and F-107's own text
names F-103 as its precondition (`findings/webtest.json:114`: *"identical to every other Mailpit
read proven this engagement (F-103)"*). `validate_corpus`'s `ROLLUP` rule
(`scripts/findings.py:418-429`) **does detect** this reference relationship — and is declared
`blocking=False`.

**(iv)** **Detection is already mechanical and already implemented.** The *comparison* — does the
chain grant more than its precondition — is judgement. But a cheap deterministic floor exists:
a finding that references another finding as its precondition must not exceed that finding's
severity unless it carries an explicit `escalation_rationale` field. That converts a silent
inflation into a forced sentence.

### FM-7 — Checklist × asset cartesian, emitted as findings

**(i)** Every check is run against every asset and every combination becomes a findings record,
including combinations the framework already knows are inapplicable before the probe is sent.

**(ii)** 36 `not_applicable` records; F-046 and F-058 (HSTS demanded of a plaintext origin); F-060
(duplicate of F-048 across two ports backed by one process).

**(iii)** The scheme is in the asset string before the request is built. The protocol mismatch is
known after the *first* probe against an asset, not after the twelfth. The single-process identity
of `:8025`/`:8026` was established during recon and written to `assets/register.jsonl:5` before the
baseline ran.

**(iv)** **Mechanically checkable, trivially.** Scheme is a string prefix; "this asset does not
speak HTTP" is one boolean per asset; process identity is already a recorded attribution signal.

### FM-8 — Blast radius asserted, never enumerated

**(i)** Severity rests on the size of the set of people who can reach the target, and that set is
described with a quantifier ("anyone", "any host") that was never given a denominator.

**(ii)** F-101, F-103, F-107.

**(iii)** *"Any host that can reach TCP 6379 on this tailnet"* (`findings/webtest.json:12`);
*"anyone who can route to the host at all, no credentials of any kind"*
(`findings/webtest.json:114`). A tailnet is a closed, ACL-governed overlay whose membership is
enumerable by its administrator — who is the client. The engagement never asked. Nothing on disk
records tailnet size, membership, ACL, or whether node sharing is enabled.

**(iv)** **Structurally mechanical, substantively judgement.** A gate can require that any finding
above `medium` carries a non-empty `reachable_population` field naming who is in the set and how
that was established. It cannot check whether the answer is true. But requiring the field converts
"anyone" from an unexamined intensifier into a claim someone has to write down — which, on this
engagement, would have produced "the operator and his own devices."

### The two questions that generate everything

FM-1 and FM-8 are the same omission at different scales: *where is this thing, and who can get to
it*. FM-5, FM-6 and FM-2 are the same omission at a different one: *what did I actually do, versus
what am I claiming*. FM-3 and FM-4 are the framework failing to carry its own answers between
components. FM-7 is volume, not risk.

A guardrail set that answers those three questions — environment, reach, and executed-versus-claimed
— covers all eleven reported findings.

## E. Counterfactual — the smallest set of checks with the largest effect

Ranked by (bad findings suppressed) / (implementation cost).

### E1. Environment classification gate — **7 of 11 findings**

*Highest ratio on this list by a wide margin.*

- **Input:** a new required `environment:` key in `scope.yaml` (`production | staging |
  development | unknown`), plus `assets/register.jsonl` and the baseline evidence files.
- **Compares:** a dev-fingerprint table against the register and evidence text. Hostname suffixes
  (`.ts.net`, `.local`, `localhost`, RFC1918 literals, `*.internal`); dev-tool service
  fingerprints in banners and `discovery_method` (`Mailpit`, `MailHog`, `mailcatcher`, `Mailtrap`,
  `Adminer`, `webpack-dev-server`, `vite`, `flower`); ephemeral storage paths (`/tmp/…`); asset or
  container identifiers matching `[-_]dev\b`.
- **On failure:**
  - `environment` absent or `unknown` → `new_engagement.py`/`gate_cli.py` refuse to approve
    Gate 1. The operator must answer the question before testing starts.
  - `environment: production` claimed but ≥1 dev fingerprint present → blocking violation naming
    the fingerprint. Either the classification is wrong or a dev component is in production, and
    both are things the operator must resolve.
  - `environment != production` → every finding is stamped `environment_at_test`, technical
    findings are capped at `low` **unless** the record carries an explicit
    `applies_to_production: true` with a stated reason, and `report.py` emits a mandatory banner:
    *"This assessment tested a development deployment. Findings that describe development-only
    components are marked and do not describe your production system."*
- **Suppresses:** F-101, F-103, F-107 (severity), F-046, F-048, F-058, F-060 (existence). Turns
  the critical and two highs into a correctly-framed environment section.
- **Cost:** one schema field, one fingerprint table, one cap in `findings.py`, one banner in
  `report.py`. Call it 150 lines and a spec paragraph.

### E2. Scheme and protocol applicability filter in `baseline_scan.py` — **2 findings + 36 records**

*Cheapest thing on the list; do it this week.*

- **Input:** the asset URL scheme, and the outcome of the first probe against each asset.
- **Compares:** (a) is `SECURITY_HEADERS["strict-transport-security"]` being evaluated against an
  `http://` origin; (b) did the first probe to this asset return a non-HTTP protocol error.
- **On failure:** (a) skip the check and record nothing — HSTS on a plaintext origin is not a
  finding; (b) stop probing that asset and emit **one** `not_applicable` coverage record naming
  all skipped checks, instead of one per check.
- **Suppresses:** F-046, F-058 outright. Collapses 36 records into 3. Also removes the
  self-contradicting impact string *"a downgrade to plaintext is not prevented"* on a plaintext
  connection.
- **Cost:** ~15 lines in `scripts/baseline_scan.py` around lines 181-185 and 390-402.

### E3. `verified_by` must differ from `discovered_by` above Low — **1 finding, repairs P2**

*Ranked third by raw ratio; build it regardless of ratio, because it is the only thing standing
between the framework and its own second design principle.*

- **Input:** the finding record.
- **Compares:** if `finding_class == "technical"` and `severity in ABOVE_LOW`, require
  `verified_by` to be present, non-empty, and `!= discovered_by`.
- **On failure:** blocking violation that **demotes severity to `low`** — following the precedent
  set by `EVIDENCE_UNRESOLVED` (`scripts/findings.py:258-263`), which demotes rather than warns
  because *"a warning about an unproven claim is exactly the thing that gets ignored under time
  pressure"* (`scripts/findings.py:56-58`).
- **Paired change:** `scripts/baseline_scan.py:233` must stop writing `verified: "executed"` on its
  own output. A scanner observation is `verified: "none"` until `rg-verify` re-runs it. This will
  correctly park every future high-severity baseline hit at `low` until someone verifies it, which
  is the intended behaviour and was not happening.
- **Suppresses:** F-005 (would have been `low` from the moment it was written).
- **Cost:** ~10 lines in `findings.py`, one line in `baseline_scan.py`, plus test updates.

### E4. Structured verification verdicts, merged mechanically — **1 finding, closes a silent-loss channel**

- **Input:** a new `findings/verification.json` — one record per reviewed finding:
  `{id, verdict: VALIDATED|REJECTED|NEEDS-WORK, gates: {1..6: pass|fail}, severity_recommendation,
  rationale_ptr}`. `verification.md` stays as the human narrative.
- **Compares:** for every finding above `low`, a verdict row must exist and its `id` must match.
  Where `severity_recommendation` differs from the record, `regen_status.py` and `report.py` take
  the **lower** of the two, and print both with the rationale pointer.
- **On failure:** no verdict row → the finding does not enter the report body; it goes to coverage
  gaps as "not verified".
- **Suppresses:** F-005 (rg-verify's correct `low` would have been applied instead of discarded).
  More importantly it means every future correct rejection actually lands.
- **Cost:** a schema, a loader, ~40 lines across `report.py` / `regen_status.py`, and a change to
  the `rg-verify` agent definition. Cheap relative to how much reasoning it currently throws away.

### E5. Impact-vs-executed lint — **2 findings**

- **Input:** `real_world_impact` and `verified` on any record at `high` or `critical`.
- **Compares:** the impact string against a non-execution marker list — `not tested`,
  `not attempted`, `not exercised`, `was not`, `reasoned from`, `well-known path`, `would allow`,
  `could also`, `not proven`. All of these appear verbatim in F-101 and F-107.
- **On failure:** non-blocking violation that routes the record into `report.py`'s open-questions
  section rather than the findings body, unless the record carries `impact_demonstrated: true` with
  its own resolving `evidence_ptr` for the impact step specifically (not the primitive step).
- **Suppresses:** F-101 and F-107 from the body at their claimed severities, while keeping both
  visible to the client as open questions — which is what they actually are.
- **Cost:** ~20 lines. Crude regex against text the agent already wrote honestly. Its whole value
  is that the disclaimer is *already in the record* and nothing reads it.

### E6. Precondition ladder — **3 findings, but needs design**

- **Input:** a new required field on any technical finding above `low`:
  `precondition: {network, prior_capability}` from a closed vocabulary —
  `network: internet | private_overlay | lan | localhost`;
  `prior_capability: none | any_authenticated_user | victim_session | local_fs_read | code_exec |
  reads_all_environment_mail`.
- **Compares:** (a) rank `prior_capability` against the capability the finding grants; if the
  precondition ranks ≥ the grant, cap severity at `low` and label the record
  `PRECONDITION-INVERTED`; (b) if `network != internet`, cap severity at `medium` unless a
  non-empty `reachable_population` string names who is in the set and how that was established.
- **On failure:** cap the severity and record the cap in the record so the report can explain why.
- **Suppresses:** F-101 / F-103 / F-107 magnitudes via (b); F-107's inversion over F-103 via (a).
- **Cost:** highest on this list — the vocabulary and the ranking table need designing, a
  mis-declared precondition is a judgement escape hatch, and the ranking will need revision after
  its first real engagement. Ranked last for that reason, not because it matters least. It is the
  only item that directly addresses the operator's complaint #2 in the general case.

### Coverage of the ranked set

E1 + E2 + E3 + E5 — the four cheapest — suppress or correctly reframe **all seven bad findings and
both misratings**, and cost roughly 200 lines plus one schema field. E4 and E6 are the durable
versions of the same corrections.

None of the six would have suppressed F-010, F-011, F-012, F-102 or F-105 — the sound results. And
none of them would have suppressed anything in section F, which is the check that matters: a
guardrail set that only subtracts is a guardrail set that makes the engagement blind.

## F. False negatives — what was real and was missed

### F.1 A client-controlled entitlement parameter on a preview route — an unjoined chain

The strongest miss, and it directly contradicts a finding that was filed.

**Stated as methodology, not as a finding.** The mechanism belongs to the upstream CMS, not to
this deployment, and the deployment's own instance has not been retested; what generalises is the
shape, not the target. The pre-audit (`pre-audit.md:188-200`) records the platform's preview route
as *"a real, present, unauthenticated content-gate simulator"*: the preview controller accepts a
**client-supplied entitlement parameter** (`anonymous|free|paid`) and synthesises a member context
of that status, attaching every active paid tier for `paid`. The controller has *"no staff-session
check of its own — it relies solely on the requester knowing the post's UUID."* Access control is
therefore a secret identifier plus a caller-asserted role — the general pattern being that an
authorisation decision is delegated to a request parameter, and the only remaining barrier is an
identifier's unguessability.

The engagement filed **F-106**: *"Paid/member-only post content is not disclosed to anonymous
callers via the public content API"* — `info`, negative, *"Anonymous readers cannot read gated
content through this key"* (`findings/webtest.json:90, 97`). One route tested; a capability-level
conclusion drawn.

The engagement held both halves of the chain and never joined them. `findings/webtest.json:97`
records that the public content-API key *"does let an anonymous caller enumerate paid-post metadata
(id/title/slug/visibility)"* — so anonymous post identifiers were in hand, in the same finding that
concluded gated content is safe.

`[UNVERIFIED]`: whether the identifier the content API exposes anonymously is the same identifier
the preview route consumes. The platform distinguishes a post's `id` from its `uuid`, and I have no
source on disk to check which fields the anonymous content API serialises. If they differ, the
bypass needs an identifier from elsewhere (a leaked preview link, referrer leakage) and the miss is
smaller. If they do not differ, F-106's conclusion is straightforwardly false. **The methodological
point does not depend on which:** a negative finding was drawn at capability level from a single
route, while the same finding recorded that the identifiers the other route needs were anonymously
enumerable. Whether the two identifier spaces coincide is exactly the question the engagement was
required to ask and did not.

Note the shape. F-107 is the engagement chaining two observed facts into a headline — against a dev
artifact. F.1 is the same chain available against a real, production-relevant control, and it was
not attempted. The capability was demonstrably present; it was pointed at the wrong target.

### F.2 MySQL remote-root reachability, recorded as a good result

Covered in B. `pre-audit.md:33-36`: `bind_address = *`, `root` and `ghost` both at grant
host `'%'`, root password `${MYSQL_ROOT_PASSWORD:-root}`. F-104 recorded *"MySQL demands
credentials on this host"* as *"a good result"* (`findings/webtest.json:63`) on the strength of one
blank-password attempt.

The engagement was constrained from credential testing by plan and by `no_destructive`, which is
correct. The defect is that the constraint did not propagate into the finding: a service that was
not credential-tested cannot be reported as credentially sound. `[UNVERIFIED]` whether the deployed
password is the compose default.

### F.3 Google SSO and WebAuthn passkey flows — the largest net-new auth surface, never enumerated

**Stated as methodology.** The route table and module names for this surface are in the pre-audit
and are not reproduced here; it is custom, live and untested, so an inventory of it is an attack
map rather than a lesson. The structural fact is what generalises: `pre-audit.md:111-129` describes
**three parallel front doors into one member session** — a magic link, a federated OIDC login, and
WebAuthn passkeys — sharing a single short-lived signed flow cookie. That shape is the classic
place authentication defects live: three code paths mint the same session, so the security of the
session is the security of the *weakest* of the three, and the shared flow cookie is a single
object every path trusts. `pre-audit.md:247-253` lists this surface as *"where real findings
live."*

The engagement found the feature flags (`<app>_sso_google_enabled`, `<app>_member_passkey_enabled`
— `assets/surface-map.md:59-62`), could not locate the endpoints because `portal.min.js` 502s
(`surface-map.md:80-84`), and recorded it as a coverage gap (`surface-map.md:204-206`,
`assets/webtest-summary.md:161-164`). That is honest and correct behaviour. It is also the
engagement spending its entire budget on Redis, Mailpit and header posture while the auth surface
the client actually built went untouched — because the component that would have revealed it was
down, which is itself a dev-state fact (FM-1).

### F.4 Everything the whitebox engagement was for

`ENGAGEMENT-B` is the only engagement with `SOURCE_CODE:github.com/<owner>/<target-repo>`
in scope (`scope.yaml:33-34`) and it produced nothing at all. The pre-audit names three confirmed,
source-visible defects that a whitebox pass targets directly:

**Stated as defect classes, not as findings.** These are live, unremediated issues in the target's
own codebase; the specific tables, columns and functions are recorded in the pre-audit and are
deliberately not reproduced here. What matters for framework design is the *class* each belongs to,
and each is a class a whitebox pass targets directly:

- **A payments ledger with no uniqueness constraint on the natural business key**
  (`pre-audit.md:280-290`). Deduplication rests solely on the payment provider's event ID, so two
  distinct completed checkout sessions for the same buyer and the same item both write ledger rows
  and both charge. Flagged as a go-live blocker and unresolved. Class: **a double-charge path
  created by an absent database constraint** — invisible to any black-box probe, trivially visible
  in a schema dump.
- **Fulfilment reachable only through the payment provider's webhook, with no fallback**
  (`pre-audit.md:291-295`). A dropped webhook charges the buyer, grants no access, and leaves a
  pending-checkout lock that rejects every retry. Class: **a single-path fulfilment with no
  reconciliation** — a correctness and money-handling defect, not a network-reachable one.
- **The reaper for that stale lock exists but has zero callers** (`pre-audit.md:296`). Class:
  **dead remediation code** — a control that is present in source, counted as mitigation by anyone
  reading for it, and never invoked. This is design judgement 4 (*a control nobody is forced to run
  is not a control*) appearing in a target rather than in RedGold.

None of these is a dev artifact. All three affect paying customers in production. All three are
visible from source and none is visible from outside. The engagement that could see the source
never ran.

`[UNVERIFIED]`: I have not read the target's source and cannot independently confirm any of the
three — they are the operator's own file:line-cited claims in the pre-audit. That is exactly why
the whitebox pass mattered.

### F.5 A live Resend key in a dev config — correctly not found, worth stating

`pre-audit.md:273`: `<app>.resendApiKey` is *"Present, real-shaped key (`re_…`, 36 chars)"*
and **not sandboxed** — the mail client posts to the live Resend API for broadcast sends.
`assets/surface-map.md:131` records *"Resend: no reference found … Negative result"*, which is a
correct black-box result: a server-side key is not visible from outside.

This is the clean illustration of the shape problem. A real, live, spend-capable credential sits in
a development config file on a laptop whose services all bind `0.0.0.0`, and the black-box
engagement could not see it by construction. The whitebox engagement could have, and did not run.

### F.6 The meta-finding

The effort was spent entirely on the half of the target where dev-state artifacts dominate and
application defects are invisible, while the half where the real defects live sat scaffolded and
untouched. Every guardrail in section E reduces the false-positive rate. **None of them increases
coverage.** The largest single improvement available to this framework is not a suppression rule —
it is running the whitebox engagement.
